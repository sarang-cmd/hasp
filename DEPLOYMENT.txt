HASP DEPLOYMENT GUIDE

Status

The repository contains static design mockups and a local web vault prototype. Neither is a production deployment. The prototype processes plaintext and keys in the Node server, uses a known sample password, has no accounts or sync, and has not received independent security review. Use synthetic data only. Do not expose the prototype to an untrusted network or put real secrets into it. The extension, desktop and mobile products are not implemented.

1. REVIEW THE EXISTING PREVIEWS

Static design mockups

Open mockups/index.html from the checkout. Open mockups/brands.html for the brand library. The mockups contain invented values and company marks. Review brand usage and access restrictions before sharing them.

If you publish a static mockup preview, prepare a separate, explicitly selected static-only output containing the mockups and any documents you intend to publish. Review every file in the output before upload. Do not publish the repository root, source code, local vault files, environment files or credentials as a static site. Links to files outside the output will not work until those files are deliberately included or the links are changed. No static deployment configuration is provided or verified here. Follow the hosting provider's current instructions for a static site and verify access restrictions, links, fonts and images after publishing. A static mockup deployment does not deploy the web vault.

Local web prototype

Install Node.js 22.6 or later and run npm install, then npm test. See README.md for the current start command and sample password. By default the server writes a sample vault to .vault/vault.json. HASP_EPHEMERAL=1 prevents this persistence for a new run. Existing vault files are not deleted by that setting.

The current server binds to 0.0.0.0 and serves plain HTTP. That may make the preview reachable from other devices on the network, and passwords and data sent over HTTP are not protected in transit. Run only in an isolated, trusted environment and block external access. Do not forward its port, publish a live preview, or treat loopback in the printed URL as proof of restricted binding. Stop the process after review. The local prototype and its sample password are not appropriate for a public or production deployment.

Deployment decisions

You: Choose whether any mockups should be shared, who can view them, and the domain and budget for any later product deployment. Review the output before publication.

Implementation agent: Inspect the current code, document the chosen architecture and deployment packaging, and demonstrate isolation and security before proposing a staging deployment. Do not assume a static Vercel configuration runs the Node server or provides durable storage.

2. PREPARE THE FUTURE PRODUCT

The steps below describe proposed work and release gates for the future product. The current prototype is not a production implementation, and these are not deployment commands for it. Do not store real secrets in mockups, test fixtures, logs, analytics, issue reports or AI prompts.

Accounts and environments

Create separate development, staging and production environments. Use separate Neon databases and authentication configuration, Vercel projects or environment scopes, R2 buckets, email settings, analytics projects and Stripe modes as appropriate. Restrict administrative access, enable MFA and keep recovery access with named owners. Record the owner, billing contact, backup policy and incident contact for each service.

Vercel and web application

Implement and review the target application and API before configuring a production build. A lockfile and test command exist for the prototype. Add and verify the target build, lint and migration commands. Connect the application repository to Vercel and configure environment values separately for development, preview and production. Mark sensitive values as secrets in the platform. Never expose server credentials through browser-accessible environment variables or client bundles.

Use a staging domain and production domain with HTTPS. Configure security headers and the authentication callback and allowed origin lists for each environment. Test sign-in, sign-out, session expiry and rejected cross-origin requests. Avoid exposing secrets in error pages, server logs, build output and source maps.

Neon database and authentication

Create separate Neon projects or appropriately isolated databases for staging and production. Create least-privilege database roles and store connection strings in the matching Vercel environment. Configure Neon Auth according to its current documentation, including allowed origins and redirect URLs. Never assume a database connection alone implements application authorization.

Review schema migrations before applying them. Test migrations and rollback or recovery procedures on staging first. Use backups appropriate to your recovery objectives, verify restoration into an isolated environment, and document the restore owner and procedure. Test ownership checks on every vault and item operation. Verify any row-level security policies with the real application database role, not an administrator role.

Encryption and security

Implement and independently review the cryptographic design before accepting real user secrets. Test key derivation, encryption, key wrapping, recovery, device revocation and sync conflicts on each supported platform. Confirm which metadata reaches the server and document the tradeoffs. Protect logs and crash reports from plaintext, tokens, one-time codes and recovery material. Obtain an external security review and resolve critical findings before launch.

Cloudflare R2

Create a separate bucket and scoped credentials for each environment. Keep buckets private. Define object retention, deletion and access rules based on the implemented import and export flows. Test signed URL expiry, upload validation and cleanup. Do not assume an object was deleted until the cleanup process and monitoring have been verified.

Resend, PostHog, Stripe and 9Router

Verify sending domains and configure SPF, DKIM and any other records requested by Resend. Test transactional email in staging. Configure PostHog only after reviewing consent and data minimization. Never send vault contents, credentials or recovery material as events.

Use Stripe test mode in staging and keep production keys separate. Verify webhook signatures, handle retries and duplicate events, and restrict the webhook endpoint. Enable live billing only after pricing, tax, legal and operational reviews.

Keep 9Router and model provider credentials on the server. AI labeling must be opt-in. Review the actual data flow before sending any material to a hosted provider. Redaction is not a guarantee that all secrets are removed. Provide a non-AI path and test the consent and failure states.

3. RELEASE CLIENTS

Browser extension

Implement and test each target browser build. Request the minimum permissions and host access needed. Check keyboard navigation, locked state, explicit fill actions and behavior on untrusted pages. Follow each store's current signing, privacy, disclosure and review requirements. Publish a staged release where available, monitor errors without collecting secrets, and retain the previous package for rollback.

Desktop application

Build installers on supported build hosts using a documented and reproducible release process. Sign Windows and macOS builds with protected signing credentials. Complete Apple notarization where required. Test installation, upgrade, uninstall, offline access and update verification. Prepare and submit the MSIX package separately for Microsoft Store review. Never distribute unsigned updates or embed signing keys in the repository.

Mobile application

Create the Android and Apple developer accounts and app identifiers. Configure signing, push capabilities only if needed, and separate staging and production endpoints. Test biometric unlock, secure storage, offline access, recovery and device loss. Submit builds and privacy disclosures through the relevant stores. Use staged rollout controls and monitor crashes without collecting vault data.

4. LAUNCH CHECKLIST

Confirm the product is implemented and the release commit is reviewed.
Confirm staging and production isolation, access controls and MFA.
Run automated tests, dependency checks, secret scanning and accessibility checks.
Complete the independent security review and test recovery and database restoration.
Verify TLS, domains, email, authentication redirects, backups and monitoring.
Set cost alerts and service limits. Assign an incident owner and document escalation.
Review privacy, terms, store disclosures and brand usage with the appropriate owners.
Run an end-to-end test with synthetic data across every release surface.
Release gradually, watch for failures and keep a tested rollback path.

For design details and proposed architecture, see PLAN.md. Provider interfaces and requirements change. Check the current documentation for each service before production setup.
